# Drive from UI — Subprocess Launch via API

## Overview

Add an API endpoint that starts `xpo drive` as a child subprocess, giving the web UI the ability to kick off and monitor drive runs. The subprocess model provides crash isolation — a failing drive doesn't take down the server. Progress is delivered through the trail watcher (xpo-7a4b19) and SSE, not through the HTTP response.

## API Endpoints

### Start a drive

```
POST /api/issues/{id}/drive
```

Request body (all optional):

```json
{
  "max_retries": 3,
  "test_cmd": "make test",
  "supervisor": "claude",
  "coder": "claude"
}
```

Response `202 Accepted`:

```json
{
  "run_id": "a1b2c3d4",
  "issue_id": "xpo-abc123",
  "pid": 12345
}
```

The `run_id` is generated by the server and passed to the subprocess so trail events can be correlated. The response returns immediately — the drive runs in the background.

**Error responses:**

- `404` — issue not found
- `409` — a drive is already running (for this issue or globally, depending on concurrency policy)
- `422` — issue is not in a driveable state (not PLANNED or DOING)

### Check drive status

```
GET /api/drive/status
```

Response:

```json
{
  "active": true,
  "run_id": "a1b2c3d4",
  "issue_id": "xpo-abc123",
  "pid": 12345,
  "started_at": "2026-07-13T10:00:00Z"
}
```

Or when no drive is running:

```json
{
  "active": false
}
```

### Stop a drive

```
POST /api/drive/stop
```

Sends SIGTERM to the drive subprocess, waits up to 10 seconds, then SIGKILL if needed. Response:

```json
{
  "stopped": true,
  "run_id": "a1b2c3d4"
}
```

## Subprocess Management

### Launch

The server starts the drive as a child process using the same binary (`os.Executable()`):

```go
cmd := exec.CommandContext(ctx, self, "drive", issueID,
    "--max-retries", strconv.Itoa(maxRetries),
    "--test-cmd", testCmd,
)
cmd.Dir = projectRoot
cmd.Env = append(os.Environ(),
    "XPO_DRIVE_RUN_ID="+runID,  // pass run ID so trail uses it
)
cmd.Stdout = logFile  // optional: capture stdout for debugging
cmd.Stderr = logFile
```

`XPO_DRIVE_RUN_ID` is an environment variable the trail writer reads to use a pre-assigned run ID instead of generating one. This lets the server know the run ID before the trail file is created.

### Process tracking

New struct in `internal/server/`:

```go
type DriveProcess struct {
    RunID     string
    IssueID   string
    Cmd       *exec.Cmd
    StartedAt time.Time
    Done      chan struct{}
    ExitCode  int
    Err       error
}
```

The server holds at most one `*DriveProcess` (single-drive concurrency for v1). A goroutine waits on `cmd.Wait()` and:

1. Records exit code and error
2. Closes the `Done` channel
3. Broadcasts a `drive_finished` SSE event with the outcome
4. Clears the active drive slot

### Lifecycle rules

- **At most one concurrent drive** (v1 simplification). Attempting to start a second returns 409.
- **Server shutdown**: sends SIGTERM to the active drive subprocess, waits up to 10 seconds, then SIGKILL.
- **Drive completes**: the wait goroutine detects exit, cleans up, broadcasts completion.
- **Orphan detection**: on server startup, check for stale trail files with no `drive_end` event. These indicate a prior crash. Don't auto-resume — surface them in the status endpoint as `{ active: false, last_orphan: { run_id, issue_id } }`.

### stdout/stderr capture

Drive subprocess output is captured to `.xpo/artifacts/<issue-id>/drive-<run-id>.log` for debugging. This is the human-readable driveLogger output (spinners, phase headers) — distinct from the machine-readable trail JSONL. Not exposed in the UI by default, but available for troubleshooting.

## Frontend

### Drive button

In `PropertySidebar.tsx`, alongside (or replacing) the "Start Work" button:

- For **PLANNED** issues: show a "Drive" button (primary action) alongside a smaller "Start Work" link for manual work.
- For **DOING** issues with an active drive: show a "Watching..." indicator with a stop button.
- For **DOING** issues without an active drive: show "Start Work" is already done, no drive button.

The Drive button calls `POST /api/issues/{id}/drive`, then the trail viewer component (xpo-575923) activates automatically.

### Drive status indicator

A small indicator in the issue detail header or sidebar showing whether a drive is active. Drives started from the CLI also show up here (detected via the trail watcher, not the process tracker).

## Capability

The endpoint requires a new capability: `issue.drive`. In authenticated mode (xpo serve), this is a distinct permission from `issue.start` or `issue.update`.

## Acceptance Criteria

1. `POST /api/issues/{id}/drive` starts a drive subprocess and returns 202 within 500ms
2. The subprocess produces trail events that are visible via SSE (verified by the trail watcher)
3. `GET /api/drive/status` correctly reports active/inactive state
4. `POST /api/drive/stop` terminates the subprocess within 10 seconds
5. Concurrent drive requests return 409
6. Server shutdown cleanly terminates an active drive subprocess
7. A crashing drive subprocess does not crash the server
8. The frontend shows a Drive button for PLANNED issues
9. CLI-initiated drives are detected and shown in the issue detail (via trail watcher, not process tracker)

## Out of Scope

- Multiple concurrent drives (future: job queue with concurrency limit)
- Remote drive execution (running drives on a different machine)
- Drive configuration UI (use defaults or config file for v1)
- Resume/retry from UI (use CLI `--resume` for now)
