# Walkthrough: ff merge folds bookkeeping into the tip

## What was built and why

Every `merge` with `strategy: ff` used to leave two things on main: the branch's commits, then a separate `xpo: merge <id>` commit holding `.xpo/issues.db` and the issue's artifacts. Squash and merge never did this; they amend the bookkeeping into their own commit. Agents were also choosing `ff` without being asked, because step 9 has them make one tidy commit first and nothing told them to leave the strategy at its default.

This fixes both: ff now amends the bookkeeping into the fast-forwarded tip, and every agent-facing text says to omit `strategy`.

## How the pieces fit together

### `MergeIssue` (`internal/exponential/merge.go`)

The flow inside the git lock is unchanged up to the bookkeeping step:
1. Merge the code (`--squash`, `--ff-only` or `--no-ff --no-commit`).
2. Commit it. ff skips this because a fast-forward makes no commit.
3. Union `issues.db` if needed.
4. `recordMerge` appends the MERGE and DONE events.
5. **Bookkeeping:** stage `issues.db` and `.xpo/artifacts/<id>/`, then commit.

Only step 5 changed. It used to branch: ff made a new commit with `xpo: merge <id>`, and everything else amended. Now **every strategy amends**:

```go
amendArgs := []string{"--amend", "--no-edit", "--no-verify"}
if opts.Strategy == MergeStrategyFF && opts.CommitMessage != "" {
    amendArgs = []string{"--amend", "--no-verify", "-m", opts.CommitMessage}
}
```

For ff, HEAD after `--ff-only` is the branch's tip commit. Amending it is safe because:
- **The commit is always new to base.** `MergeIssue` refuses a branch with `BranchStats.Commits == 0` before taking the lock, so a fast-forward always moves HEAD. The amend therefore never rewrites a commit that was already on main (and possibly pushed).
- **The branch and worktree are removed right after.** Nothing else points at the pre-amend commit. With `keep_branch`, the kept branch ends one commit behind main's tip (same content minus bookkeeping). It's history only, so that's acceptable.

With a multi-commit branch, only the tip is amended. The earlier commits land on main unchanged.

`--no-verify` stays: hooks already ran when the branch's commits were made in the worktree.

`result.MergeSHA` was already read from HEAD *after* bookkeeping, so it reports the amended SHA with no change.

### Custom commit message

The `xpo: merge %s` default is gone, so the ff case in the default-message switch is now a no-op with a comment. An explicit `commit_message` used to become the subject of the bookkeeping commit. To keep it meaningful, it now rewords the amended tip. Without that, `--no-edit` would silently drop it.

### Failure fallback

This is unchanged. If the amend fails, `.xpo` is unstaged, the events stay recorded but uncommitted (they go out with the next commit), and a warning is returned. For ff, main is left at the untouched branch tip.

### Agent guidance

| Where | Change |
|---|---|
| `mergeToolDescription` (`tools.go`, extracted to a const so it can be tested) | "Omit `strategy` unless the user asks for a specific one." |
| `MergeToolInput.Strategy` jsonschema (`jsonio/input.go`) | Same note |
| `GenerateMCPToolsRef()` `merge` row (`agents.go`) | "Call it without a `strategy` unless the user asks for one" |
| `GenerateSkillMD()` step 9 (`agents.go`) | "Call the xpo MCP server's `merge` tool without a `strategy`" |

The installed copies in `.claude`, `.codex` and `.opencode` were regenerated by calling `WriteAgentSkill` directly, the same code path `xpo init` uses. This also brought in the `unlink` row from xpo-9d5d00, whose template change had not been regenerated. Other projects get the new text when they re-run `xpo init` with a new binary; the health check reports "Skill out of date" until then.

## Key decisions

- **No guard for a no-op ff.** The spec first planned one: keep a separate commit when HEAD didn't move. It was dropped because `MergeIssue` already rejects branches with no commits ahead, so the guard would be dead code.
- **Reword the tip on an explicit ff `commit_message`**, rather than ignore it. The user asked for that message, and the tip is the only commit xpo writes to in an ff.
- **Amend only the tip of a multi-commit ff.** That's enough to keep the bookkeeping out of a commit of its own.
