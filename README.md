# Beats

A JSONL-based issue tracker that is committed to Git together with your project.

## Model
Beats is based on an Event-sourcing model, with snapshots and archiving. Every line is an immutable event, not a task definition.

### Why this works best:
- Merge Conflict Avoidance: You almost always append new lines to the end of the file. Git handles appending from multiple branches much better than modifying the same lines in the middle of a file.
- History: You get a full audit trail of who moved a ticket and when, using `beats history <id>`.

### How to Build the Board (The "Projection")
To view the Kanban board, `beats` reads the JSONL file from top to bottom and builds the current state in memory:
- Read Line 1: Create Epic "Refactor Backend".
- Read Line 2: Create Task "Design Schema" under Epic-1.
- Read Line 3: Change Task-10 Status to "DOING".
- Render: Draw the board based on the final object state.

## Implementation

### 1. Kanban Board (Status Handling)
You need a strict schema for the status field.

Schema: ["BACKLOG", "PLANNED", "DOING", "BLOCKED", "DONE"]
Visualization: Your tool parses the JSONL and groups items by this field.
Column 1: Filter where status == 'PLANNED'
Column 2: Filter where status == 'DOING'

### 2. Epics & Child Tasks (Hierarchy)
You handle this via a parent_id field (foreign key).
- Epics: Items where kind == "EPIC".
- Tasks: Items where kind == "TASK" and parent_id is not null.
- Visualization: When rendering the board, you can "Swimlane" the board by Epics.
- Row 1 (Epic A): Show all tasks where parent_id == Epic A.

### 3. ID Generation (Crucial for Git)
You cannot use sequential integers (1, 2, 3) because two developers on different branches might both create "Task #4".
Solution: Use Short UUIDs or Hash-based IDs (e.g., a1b2c3d) generated by your CLI tool when an issue is created. Let's use length-6 nano-ids from the alphabet [a-Z0-9].

### 4. Snapshots
Beats also has a "Checkpoint" (Snapshot) System. You do not need to replay history from the beginning of time (The Big Bang) every time you run a command. You only need to replay from the last "Checkpoint."
This is how database logs (WALs) and Git itself work.

How it works:
`.beats/issues.jsonl` (The Log): Contains the immutable history (events).
`.beats/issues.snapshot.json` (The Cache): Contains the calculated state of the board as of a specific Event ID.

Beats writes a new snapshot file automatically every 5,000 issues, or manually with `beats snapshot`. This snapshot is **local only** the file is part of `.gitignore` so we don't get merge conflicts on the snapshot. It's automatically generated the first time a user views the backlog.

### 5. Archive
After 6 months, you probably have 2,000 "DONE" tickets that no one looks at. You don't need to load them into the Kanban board RAM every time.
The "Archive" Rotation: You can split your data into two files:
`.beats/issues.jsonl`: Only contains active events and recent history.
`.beats/archive.jsonl`: Contains events for tasks that are archived.

How to implement: When a task has been in DONE status for > 30 days, move all events related to that Entity ID from the `issues.jsonl` to `archive.jsonl`.
Result: Your main file stays small (e.g., 5,000 lines).
Trade-off: If you want to search old tickets, you have to use a special flag `beats search --all`

Manual archiving can be triggered with `beats archive`

### The 3-File Architecture
This leaves us with the final 3-file architecture:

#### 1. issues.jsonl (The "Hot" Log)
Content: Contains the full event history (Created, Moved, Commented) for every issue that is currently Active (PLANNED, DOING, etc.) or recently DONE.
Role: This is the Source of Truth.
Git Behavior: Very friendly. Developers append lines to the bottom. Merge conflicts are rare.

#### 2. issues.snapshot.json (The "Checkpoint")
Content: A single JSON object representing the calculated final state of the board as of a specific line number in issues.jsonl.
Role: Read Optimization. When the CLI starts, it loads this first. Then it only needs to read the few lines in issues.jsonl that were added after the snapshot was generated.
Git Behavior: High conflict risk (see warning below).

#### 3. archive.jsonl (The "Cold" Storage)
Content: The event history for issues that were closed long ago.
Role: Audit Trail. It keeps the main file small. You only read this file if you run a command like tracker search --all.
Git Behavior: Rarely touched. Only updated during "cleanup" cycles.

#### Directory Structure
Use a .beats subdirectory.

While putting files in the root is "simple," a dedicated hidden folder is the standard for developer tools (like .git, .vscode, .github) for very good reasons.
Here is why .beats/ is the better engineering decision:

 1. Root Directory Hygiene
  
  Your project root is prime real estate. It should only contain the absolute essentials for understanding the project (README, main.go, go.mod, Dockerfile).
  Root: Adds 3+ files (issues.jsonl, snapshot, archive, maybe config). It looks messy.
  Subdirectory: Encapsulates everything. Your root stays clean.

2. The "Database" Mental Model

  You are essentially embedding a small database in your repo.
  If you have 50,000 archived events, archive.jsonl might be 10MB. You don't want a 10MB file sitting next to your README.md.
  Grouping them in a folder reinforces that these files work together.

3. Future Proofing (Configuration & Assets)

  Right now, you just have data. But soon you will likely want:
  config.yaml (Custom columns, colors, tag rules).
  templates/ (Issue templates for bugs vs features).
  hooks/ (Scripts to run before/after updates).
  If you are in the root, you can't easily add these without making a mess. In a folder, you just add them.

## Workflow
Here is how a user interacts with the system on a day to day basis:

### 1. Creating an issue
Either via CLI `beats create -t <epic|task> -p <parent_id> "Description"` or Kanban UI. Appends a new line to JSONL, `git commit -am "<description>" .beats/issues.jsonl`

### 2. Updating the status
Either via CLI `beats update <id>` or Kanban UI. Appends a new line to JSONL with the update event. Commits like before.

## The GUI
We follow the Single Binary Web App" pattern. Tools like Docker Desktop, Syncthing, and Hugo use similar concepts to provide a GUI without requiring the user to install Node.js or a web server.
Since you are using Go, you have a "superpower" for this: go:embed.
Here is how you would architect beats to bundle a full React Kanban board inside a single CLI binary.

### The Architecture: "The Embedded GUI"
The magic happens in the build process. You don't ask the user to run npm start. Instead, you "bake" the React HTML/JS/CSS files directly into the Go executable variables.

### The User Experience (beats board)
When the user types beats board, the CLI acts as a localized web server.
Load State: The Go CLI parses issues.jsonl (and snapshots) into memory.
Start Server: It spins up localhost:9123.
Auto-Open: The CLI automatically opens the user's default browser.
Live Updates:
Frontend: The React app fetches GET /api/issues on load.
User Action: User drags a card from PLANNED to DOING.
Request: React sends POST /api/move {id: "task-1", status: "DOING"}.
Backend: Go appends the event to issues.jsonl and updates its in-memory state.
Response: Go returns 200 OK. React updates the UI.
Pro-Tip: Auto-Open Browser Use the pkg/browser library in Go to make it seamless.

### Handling React Routing (SPA Fallback)
Since it's a Single Page App, if the user refreshes on http://localhost:9123/epic/beats-afge1, the Go server must not look for a file named /epic/1. It must serve index.html and let React handle the route.

The Fix in Go:
```go
// If file not found in embedded FS, serve index.html
r.NoRoute(func(c *gin.Context) {
    path := c.Request.URL.Path
    // Check if it's a file request (has extension like .js, .css)
    if filepath.Ext(path) != "" {
        c.FileFromFS(path, http.FS(webFS))
    } else {
        // Otherwise serve index.html for all "pages"
        c.FileFromFS("index.html", http.FS(webFS))
    }
})
```

### Why this is a great choice
Zero Dependencies: The user doesn't need Node.js installed. They just download the beats binary.
Fast: Go serves static files incredibly fast.
Security: The API is local-only (bound to 127.0.0.1), so it's secure by default.
Git Friendly: You are still writing to the local issues.jsonl file. You can leave the board running, switch branches in your terminal, and simply refresh the browser to see the new branch's tickets (assuming you reload the file in Go or restart the server).

## The CLI
Here is a clean, developer-friendly CLI design for `beats`.
This structure is designed to be implemented easily using the **Cobra** library in Go. It prioritizes speed of entry (short aliases) and clear intent.

### 1. The Command Hierarchy

```text
beats [command] [arguments] [flags]
```

#### Global Flags

  * `--path`: Path to the project root (default: current directory).
  * `--json`: Output command results as JSON (useful for piping).

-----

### 2. Detailed Command Reference

#### Setup

**`beats init`**
Initializes the `.beats` directory and creates the initial `issues.jsonl` file.

  * **Check:** Fails if not inside a git repository.
  * **Action:** Adds `.beats/` to `.gitignore` (conditionally, if you decide to ignore local config).
  * **Example:** `beats init`

-----

#### Creation

**`beats add [title]`**
Creates a new entity. By default, it creates a **Task**.

  * **Arguments:** `title` (Required, quoted string).
  * **Flags:**
      * `-e, --epic` (Bool): Create an Epic instead of a Task.
      * `-p, --parent <id>`: Link this task to a parent Epic ID.
      * `-d, --desc <text>`: Add a description.
      * `-s, --sp <points>`: Set initial estimate.
  * **Aliases:** `new`, `create`
  * **Example:**
      * `beats add "User Authentication" --epic`
      * `beats add "Login Form" -p epic-1 -s 3`

-----

#### Status Workflow (The "Moves")

These are shortcut commands that generate `UPDATE` events specifically for the `status` field.

**`beats planned [id]`**
Moves an issue to the `PLANNED` column.

  * **Example:** `beats planned task-10`

**`beats start [id]`**
Moves an issue to `DOING`.

  * **Aliases:** `s`, `do`
  * **Example:** `beats start task-10`

**`beats done [id]`**
Moves an issue to `DONE`.

  * **Aliases:** `d`, `close`, `fix`
  * **Example:** `beats done task-10`

**`beats blocked [id]`**
Moves an issue to `BLOCKED`.

  * **Flags:**
      * `-b, --by <id>`: The ID of the issue causing the block.
      * `-r, --reason <text>`: A text explanation.
  * **Example:** `beats blocked task-10 --by task-5 --reason "Waiting on API"`

-----

#### Updates & Management

**`beats update [id]`**
General purpose update for fields other than status.

  * **Flags:**
      * `--title <text>`
      * `--desc <text>`
      * `--parent <id>` (Move task to different epic)
  * **Example:** `beats update task-10 --title "Login Form V2"`

**`beats estimate [id] [points]`**
Updates the story point estimate (Complexity).

  * **Arguments:** `points` (Integer or float).
  * **Example:** `beats estimate task-10 5`

**`beats log [id] [points]`**
Logs "Burned" effort against a task. Unlike `estimate` (which sets the total size), this *appends* a work log entry.

  * **Arguments:** `points` (The amount of effort spent *since last log*).
  * **Internal Event:** Generates a `WORK_LOG` event type, not just an update.
  * **Example:** `beats log task-10 2` (Logged 2 points of work).

-----

#### Visibility

**`beats board`**
Starts the embedded web server and opens the Kanban board.

  * **Flags:**
      * `-p, --port <int>`: Custom port (default: 9123).
      * `--no-open`: Do not auto-open the browser.
  * **Example:** `beats board`

**`beats history [id]`**
Prints the audit trail for a specific issue.

  * **Output:** ASCII table showing `Time | User | Action | Details`.
  * **Example:** `beats history task-10`

### 3. Implementation Logic (Event Mapping)

To make these commands work with your JSONL architecture, here is how they map to **Event Types**:

| Command | Event Type | JSON Payload Data |
| :--- | :--- | :--- |
| `add` | `CREATE` | `{ "kind": "TASK", "title": "...", "parent_id": "..." }` |
| `update` | `UPDATE` | `{ "title": "..." }` |
| `start` | `UPDATE` | `{ "status": "DOING" }` |
| `blocked`| `UPDATE` | `{ "status": "BLOCKED", "blocked_by": "task-5", "block_reason": "..." }` |
| `estimate`| `UPDATE` | `{ "estimate": 5 }` |
| `log` | `WORK_LOG` | `{ "amount": 2 }` (Aggregated at read-time) |

### 4. Interactivity for the CLI
Since nobody likes typing UUIDs (`beats start a1b2c3d`), you should add **Interactive Selection** using a library like **Bubble Tea**.

If the user types `beats start` (without an ID):

1.  The CLI fetches all recent tasks in `TODO` state.
2.  It presents a list:
    ```text
    ? Select task to start:
      > [task-1] Fix Login
        [task-2] Update CSS
    ```
3.  The user hits Enter.
4.  The CLI executes the command for that ID.

-----

### 5. Maintenance Commands

#### **`beats snapshot`**

Manually forces a regeneration of the `.beats/issues.snapshot.json` file.

  * **Why run this?**
      * You just merged a massive branch with 50 new tasks and the CLI feels slow.
      * You manually edited `issues.jsonl` to fix a typo and want to ensure the cache matches.
  * **Logic:**
    1.  Reads `issues.jsonl` from line 0.
    2.  Reconstructs the full state in memory.
    3.  Writes the state object to `issues.snapshot.json`.
    4.  Updates the `last_processed_event` pointer.
  * **Example:** `beats snapshot`

#### **`beats archive`**

Moves "stale" completed issues from the hot log to cold storage.

  * **Flags:**
      * `--days <int>`: Archive issues closed more than X days ago (Default: 30).
      * `--dry-run`: Show what *would* be archived without moving data.
  * **Logic:**
    1.  Identifies all tasks where `status == DONE` AND `updated_at < (Now - Days)`.
    2.  Extracts **all** events for those IDs from `issues.jsonl`.
    3.  Appends them to `.beats/archive.jsonl`.
    4.  Removes them from `issues.jsonl`.
    5.  Automatically runs `beats snapshot` immediately after (to heal the state).
  * **Example:** `beats archive --days 60`

-----

### 6. Utility Commands

#### **`beats list` (aliased as `beats ls`)**

A terminal-based list of issues. This is crucial for quick checks.

  * **Flags:**
      * `--status <status>`: Filter by status (e.g., `todo`, `doing`).
      * `--epic <id>`: Filter by parent epic.
      * `--mine`: Filter by assignee (current user).
  * **Output:** A pretty-printed ASCII table.
  * **Example:** `beats list --status doing`

<!-- end list -->

```text
ID       TITLE               STATUS   EPIC
task-10  Design Schema       DOING    epic-1
task-12  Fix Login Bug       DOING    -
```

#### **`beats show`**

Shows the current status (and history of) the given issue. If given an epic ID, also shows the status of the child tasks (plus summary stats, like rolled up estimated SPs, rolled up burned down SPs, statuses)

#### **`beats doctor`**

Since `issues.jsonl` is a plain text file, developers *will* open it in VS Code and edit it manually. Sometimes they will break the JSON syntax (e.g., missing a comma or brace).

  * **Logic:**
      * Scans `issues.jsonl` line-by-line.
      * Validates that every line is valid JSON.
      * Checks for logical inconsistencies (e.g., an event referencing a `parent_id` that doesn't exist).
      * **Auto-fix:** Can offer to comment out corrupt lines.
  * **Example:** `beats doctor`

#### **`beats config`**

A helper to view or edit the local configuration.

  * **Actions:**
      * `beats config list`: Shows current settings.
      * `beats config set user "Alice"`: Sets the local username for event logging.
  * **Why this matters:** When you run `beats done`, the system needs to know *who* did it. By defualt we try to guess from `git config user.name`, but this allows an explicit config or override.

## Configuration

### Locations
Configuration is loaded from the following locations in order (precedence: high to low):
1. Environment variables (`BEATS_...`)
2. Local config: `.beats/config.yaml`
3. User config: `~/.config/beats/config.yaml`
4. Default values

### Options

| Key | Environment Variable | Default | Description |
| :--- | :--- | :--- | :--- |
| `editor` | `BEATS_EDITOR` | `$EDITOR` or `vim` | The editor to use for entering descriptions. |
| `auto_commit` | `BEATS_AUTO_COMMIT` | `false` | Automatically commit changes to `issues.jsonl` using git. |
| `style.theme` | `BEATS_STYLE_THEME` | `default` | UI theme (currently only `default` supported). |

### Example `config.yaml`

```yaml
editor: "nano"
auto_commit: true
style:
  theme: "default"
```
